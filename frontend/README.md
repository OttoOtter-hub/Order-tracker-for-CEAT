# CEAT Order Tracking — Frontend (v2 Phase 11: actual containers)

React SPA for the CEAT Order Tracking backend (see [../README.md](../README.md)
for the API). Phase 1 rebuilt auth + routing scaffolding with placeholders;
Phases 2–3 built the backend's PI-card upload/approval/backorder-parsing
endpoints with no UI. Phase 4 built the real screens: a shared card list
for both roles, a detail page with the file/approval flows, and an ops-only
backorder upload screen. Phase 5 added Excel export buttons on top of those
screens. Phase 6 moved the backorder-export button onto the shared PI list
(`/ops/pi` and `/client/pi`) and opened it to `client` too, scoped to their
own customer. Phase 7 added a client-only "priority mode" on the PI detail
page's line items table — the first step of a shipment-planning feature.
Phase 7.1 added a "Сбросить" button next to it, bulk-zeroing a card's
priorities in one backend call behind a confirm dialog. Phase 7.2 made
priority integer-only. Phase 7.3 restricted the "Сбросить" button's
visibility to only while priority mode is on — see "Приоритизация
позиций" below. Phase 9 added the "Готово к отгрузке" section (container
planning, marking files) for both roles — see "Готово к отгрузке (Фаза 9)"
below. Phase 11 added the "Готовые контейнеры" section (containers CEAT has
already shipped, from the weekly file) and the "Отправлено" field on the PI
detail page — see "Готовые контейнеры (Фаза 11)" below.

## Стек

- React + TypeScript + Vite
- React Router (declarative `<Routes>`)
- TanStack Query — `staleTime: 30_000` on queries; every mutation
  invalidates `["proforma-invoices"]` (and `["backorder-uploads"]` where
  relevant) on success rather than manually patching the cache everywhere
- shadcn/ui (Radix + Tailwind v4) — `Card`, `Badge`, `Dialog`, `Table`,
  `Button`, `Input`, `Textarea`, `Separator`, `Label`, `Sonner` (toast)
- Plain `<input type="file">` — no drag-drop, not asked for and not needed
  at pilot scale

## Запуск

```bash
cp .env.example .env   # VITE_API_URL, по умолчанию http://localhost:3000
npm install
npm run dev
```

Поднимется на `http://localhost:5173`. Бэкенд — отдельно (корневой README),
с `CORS_ORIGIN` разрешающим этот origin.

## Список карточек (`pages/shared/PiListPage.tsx`)

Один компонент на оба маршрута, тот же принцип, что `BackorderPage` в v1:
нет ни одной role-специфичной ветки в самом списке кроме кнопки "Загрузить
проформу" (`user.role === "ops"`) — скоуп по customer для `client` уже
применяется на бэкенде (`GET /proforma-invoices` + `CustomerScopeInterceptor`,
см. корневой README).

- **Плитка** (`PiCard.tsx`): номер PI, `StatusBadge` (5 реальных статусов —
  `missing_pi_document`/`missing_signed_document`/`signed`/
  `replacement_pending`/`archived_shipped`; в задании их описали как "4
  состояния", но `replacement_pending` — реальный вычисляемый статус
  бэкенда, скрывать его на карточке значило бы прятать релевантную
  информацию, поэтому показаны все 5), уникальные SO-номера из
  `lineItems`, `totalQty`/`qtyPending`/`containersPending`/план недели
  (`currentWeekPlanContainers`/`currentWeekPlanQty`).
- **Архивные карточки** (`isArchivedShipped`) по умолчанию скрыты из
  списка; чекбокс "Показать архивные" их проявляет — тогда они рендерятся
  приглушёнными (`opacity-60 grayscale-[50%]` на `PiCard`), но остаются
  кликабельными, не read-only относительно самого клика.
- **"Загрузить проформу"** (ops, `UploadPiDialog.tsx`) — верхнеуровневая
  кнопка, не привязана к конкретной карточке: номер PI распознаётся из
  имени файла на бэкенде (`upload-pi`), при успехе — редирект на
  `/{basePath}/pi/{id}` созданной/дозаполненной карточки.

## Детальная страница (`pages/shared/PiDetailPage.tsx`)

### Блок "Файлы"

- **Исходная проформа**: есть файл → "Скачать" + кто/когда загрузил, и для
  `ops` (если нет активного предложения замены) — кнопка "Предложить
  замену" (диалог с `FileUploadForm`, `propose-replacement`). Нет файла →
  для `ops` инлайновая `FileUploadForm` (тот же `upload-pi`, что и
  верхнеуровневая кнопка — сервер сам решает, дозаполнить эту карточку или
  создать новую, по номеру из имени файла); для `client` — просто текст
  "ещё не загружена".
- **Подписанный файл**: есть → "Скачать" + метаданные. Нет → для `client`
  инлайновая `FileUploadForm` (`upload-signed`); для `ops` — текст.
- **Доп. файлы**: список со "Скачать" + кто/когда/описание, и
  `AddAdditionalFileForm` (файл + необязательное описание) — доступна
  обеим ролям, без лимита на количество.

### Блок предложенной замены

Рендерится только если `pendingReplacementFileUrl` не пуст: оба файла
(текущий и предложенный) рядом со своими кнопками "Скачать", кто/когда
предложил; для `client` — кнопки "Одобрить"/"Отклонить"
(`replacement-decision`, без промежуточного подтверждения — сам факт клика
и есть решение); для `ops` — просто "Ожидает решения клиента".

### Таблица позиций (`PiLineItem`)

`material_num`, `material_desc`, `balance_to_be_delivered`, `quantity`,
`mt`, `load_factor`, `loadability`, план недели
(`current_week_dispatch_load_factor` / `current_week_dispatch_qty`) —
read-only, сортировка по клику на заголовок через существующие
`useTableSort`/`SortableHead` (тот же паттерн, что везде в v1). **Фаза 7**
добавила девятую колонку "Приоритет" — read-only вне режима
приоритизации/для `ops`, интерактивная для `client` в режиме
приоритизации, см. "Приоритизация позиций" ниже.

**Строка "Всего"** — первая строка `<TableBody>`, отдельно от
`sortedLineItems.map(...)`, поэтому сортировка на неё не влияет (только
переставляет строки данных под ней) и она видна сразу, без скролла — не
нужна отдельная "закреплённая" реализация. Выделена визуально
(`bg-muted/50 font-semibold`). Источник значений — по колонкам:

- Остаток / Кол-во / план недели (Qty-часть) — не пересчитываются на
  фронте, берутся готовыми с бэкенда: `pi.qtyPending`, `pi.totalQty`,
  `pi.currentWeekPlanQty` соответственно (`computePiAggregates` на бэкенде
  считает их прямой суммой тех же самых колонок, см. корневой README —
  1-в-1 совпадают по смыслу, пересчитывать то же самое на клиенте было бы
  лишней работой).
- MT / Load Factor / план недели (Load Factor-часть) — суммируются на
  фронте (`sumField`) по **всем** `pi.lineItems`, не по `sortedLineItems` —
  для готовых агрегатов бэкенда нет 1-в-1 соответствия (`totalContainers`
  и `currentWeekPlanContainers` считаются через `Qty/Loadability`, а не
  прямой суммой этих колонок, см. корневой README про находку в Фазе 3.1 —
  использовать их здесь означало бы показывать не то число).
- Loadability — не суммируется вообще (константа на SKU, не величина) —
  прочерк "—".
- Приоритет — пустая ячейка в самой строке "Всего"; сводные значения
  вместо этого показаны в отдельной строке "Приоритет" сразу под "Всего",
  см. "Приоритизация позиций" ниже.

## Скачивание файлов (`lib/download.ts`)

`GET /files/:id/download` требует `Authorization: Bearer <token>` — простой
`window.open(url)` не шлёт этот заголовок и получил бы `401`. `openFile()`
делает `fetch` с токеном, получает `blob`, открывает его как `blob:` URL.

**Важный нюанс, найденный только живым тестом в браузере (не curl):**
`window.open()` обязан быть вызван синхронно внутри обработчика клика —
после `await fetch(...)` он для браузера уже не выглядит прямым следствием
пользовательского жеста, и popup-блокировщик его молча блокирует. Фикс:
`openFile()` сразу открывает пустую вкладку (`window.open("", "_blank")`,
синхронно, до всякого `await`), и только после того как `fetch` отработает
— направляет её на `blob:`-URL (`target.location.href = objectUrl`). Если
даже синхронный `open()` заблокирован — резервный вариант: навигация в той
же вкладке (`window.location.href`), не тихий отказ.

**`downloadFile()` (Фаза 5)** — для "сохрани этот файл" (xlsx-экспорты), а
не "покажи его": `<a download>`-клик, не `window.open` — popup-блокировщик
тут ни при чём (клик по существующему в DOM элементу — не запрос нового
окна), так что не нужен тот же трюк с синхронным пустым окном. Имя файла
берётся из `Content-Disposition` ответа (см. корневой README про
`exposedHeaders`), с фолбэком на дефолтное имя, если заголовок почему-то не
пришёл. Используется `exportPiXlsx()`/`exportBackorderXlsx()` (`api/`).

## Приоритизация позиций (Фаза 7)

Первый шаг режима планирования отгрузок — client проставляет, сколько из
остатка каждой позиции приоритизировать. Всё на `PiDetailPage.tsx`, плюс
новый `PriorityInput.tsx` для самой ячейки-инпута (`pages/shared/`) и
`api/piLineItems.ts` для `PATCH /pi-line-items/:id/priority`.

- **"Режим приоритизации"** — кнопка-переключатель в шапке карточки, видна
  только `client` (`user.role === "client"`) и только если карточка не
  архивная (`!pi.isArchivedShipped`) — те же два условия, под которыми
  бэкенд вообще позволяет писать `priorityQty`. Переключает
  `isPriorityMode`; текст кнопки меняется "Режим приоритизации" ↔ "Готово".
- **`editModeActive = isClient && isPriorityMode && !pi.isArchivedShipped`**
  — вычисляется заново на каждом рендере, а не просто читает
  `isPriorityMode`: если карточка успела заархивироваться в фоне (или
  что-то ещё изменило доступность) в открытой вкладке, инпуты пропадут
  сами, без отдельной логики "выключить режим при архивации".
- **`PriorityInput.tsx`** — чисто контролируемый компонент: number-инпут
  (`min=0`, `max=maxInt` — `Math.floor(balanceToBeDelivered)`, см. ниже) +
  кнопка "Весь остаток" + живая строка `= X.XX конт.`
  (`priorityQty / loadability`, `toFixed(2)`, скрыта если `loadability`
  отсутствует/`0`). Не знает ни о debounce, ни о сохранении — тот, кто его
  рендерит, решает, что делать с новым значением.
  **Фаза 7.2**: инпут и кнопка раньше клэмпили каждый по-своему прямо в
  своих обработчиках (`onChange`/`onClick`) — ровно та форма дублирования,
  которую ранее (после Фазы 7.1) уже разбирали на предмет "ручной ввод
  трактуется иначе, чем кнопка" (см. корневой README — дублирования тогда
  не нашлось, но риск был реальным). Теперь оба идут через один
  `commit(raw)`: `Math.round(raw)`, клэмп к `[0, maxInt]`,
  `maxInt = Math.max(0, Math.floor(max))` — приоритет считает целые шины,
  не доли; `step={1}` на самом `<Input>` — но это только про нативные
  стрелочки/spinner, не про то, что можно напечатать руками, поэтому
  реальная защита — именно округление в `commit()`, а не HTML `step`.
- **Драфт-стейт на `PiDetailPage`**: `priorityDrafts` (`Record<lineItemId,
  number>`) — единственный источник истины для того, что сейчас показано
  в инпутах и что суммируется в сводной строке. Инициализируется из
  `pi.lineItems` в `useEffect`, привязанном к `pi?.id`, **не** к `pi`/
  `pi.lineItems` — иначе фоновый рефетч (например, из-за debounce-сохранения
  одной строки) сбрасывал бы ещё не сохранённый черновик другой строки,
  которую пользователь как раз печатает. Сброс происходит только при
  переходе на другую карточку.
- **Сохранение — debounce 500мс на строку**
  (`priorityDebounceTimers` — `Record<lineItemId, Timeout>` в `useRef`):
  каждый `onChange` сразу обновляет `priorityDrafts` (мгновенный визуальный
  отклик и пересчёт сводной строки) и одновременно перезапускает таймер
  на 500мс для этой конкретной строки; сработавший таймер шлёт
  `PATCH .../priority` с последним значением. Разные строки не блокируют
  друг друга — таймеры независимые, по `lineItemId`. Ошибка сохранения
  (в т.ч. `400` от сервера на "остаток внезапно оказался меньше" — фронт
  уже не даёт ввести больше через `max`, но сервер — источник истины,
  если что-то разошлось) — `toast.error`, значение в инпуте не
  откатывается автоматически (тот же принцип "ошибка не безмолвная", что и
  везде в проекте, без лишней сложности отмены).
- **Сводная строка "Приоритет"** — вторая жирная строка `<TableBody>`,
  сразу под "Всего" (не встроена в неё — separate row, как и просили).
  Использует **не** серверные `pi.priorityTotalQty`/
  `priorityTotalContainers`, а `livePriorityTotals` — `useMemo` по
  `priorityDrafts`, пересчитывается на каждое изменение черновика,
  синхронно, без ожидания round-trip к серверу (то самое требование "не
  ждёт сохранения"). Контейнеры — той же формулой группировки по
  `loadability`, что и бэкенд (`sumByLoadabilityGroups`,
  `lib/sumByLoadability.ts` — см. корневой README про дублирование
  формулы между фронтом и бэком, тут та же причина). Серверные
  `priorityTotalQty`/`priorityTotalContainers` (добавлены в ответ
  `GET /proforma-invoices/:id` этой же фазой, см. корневой README) сейчас
  этой страницей не читаются вообще — они существуют для API как таковой,
  на случай, если что-то ещё захочет их напрямую, не пересчитывая; после
  сохранения обе стороны всё равно сходятся к одному и тому же числу.
- **Read-only режим** (не-`client`, или `client` вне режима
  приоритизации): ячейка колонки "Приоритет" — просто
  `formatNumber(item.priorityQty)` (никогда не `null`, так что реально
  либо число, либо "0" — прочерк не показывается, значение всегда
  осмысленно как "текущий приоритет").

### "Сбросить" (Фаза 7.1, видимость сужена в Фазе 7.3)

Кнопка рядом с "Режим приоритизации". **Фаза 7.1** показывала её при том
же условии, что и сам переключатель (`isClient && !pi.isArchivedShipped`)
— видна и вне режима редактирования, что оказалось лишним: кнопку
массового необратимого действия не нужно видеть в обычном просмотре
карточки. **Фаза 7.3** сузила условие до `isPriorityMode` — кнопка
видна строго пока режим приоритизации включён, пропадает сразу при
"Готово". Логика самого действия (confirm, `PATCH .../reset-priority`,
отмена pending-дебаунсов) не менялась — правка только в JSX-условии
рендера. По клику —
`window.confirm("Сбросить весь приоритет по этой проформе?")`; отказ от
подтверждения — no-op, ни одного запроса на сеть (проверено вживую, см.
ниже). Подтверждение — вызывает `useResetPriorityMutation` (`api/
proformaInvoices.ts`), `PATCH /proforma-invoices/:id/reset-priority`
**один раз**, не по одному `PATCH .../priority` на строку — бэкенд сам
обнуляет всё одним `UPDATE` (см. корневой README).

Перед самим запросом `handleResetPriority` явно чистит все ожидающие
`priorityDebounceTimers` (`clearTimeout` на каждый, затем сброс map) —
если пользователь успел напечатать что-то в инпут(ы) и не дождался
500мс-debounce, отменённый таймер не даст устаревшему
`PATCH .../priority` прилететь поверх свежего сброса и молча вернуть
приоритет на не-нулевое значение. `onSuccess` — зануляет
`priorityDrafts` сразу из `updatedPi.lineItems` ответа (не просто
константой "0" по всем ключам, хотя результат тот же — так драфт-мап
остаётся построенным из актуального набора id, если бы состав строк
успел где-то разойтись) и toast об успехе; `onError` — toast с текстом
ошибки, состояние на экране не трогается (тот же "ошибка не безмолвная"
принцип, что и у обычного сохранения приоритета).

Живая проверка (Claude Browser + curl, dev-сервер, реальная Neon-БД, см.
корневой README для полного сценария и точных цифр): `client` включил
режим, ввёл значение в первую строку — сводная строка и "= X конт." под
инпутом обновились мгновенно; "Весь остаток" на второй строке — то же
самое; оба `PATCH` ушли по debounce и вернули `200`; переключение в
read-only показало сохранённые значения без потерь. `ops` тем же URL видит
те же цифры read-only, без кнопки режима и без инпутов вообще.

Живая проверка "Сбросить": клик без подтверждения диалога — ни одного
сетевого запроса; клик с подтверждённым `window.confirm` (застаблен через
`javascript_tool` — в автоматизированном браузере native `confirm()`
иначе тихо отклоняется, что тоже полезно оказалось увидеть — это и есть
корректное поведение "случайный клик ничего не делает") — один
`PATCH .../reset-priority`, обе строки вернулись с `priorityQty: "0.00"`
и одинаковым `updatedAt` (один `UPDATE`, не два последовательных), таблица
и сводная строка обнулились сразу, без перезагрузки страницы. Отдельно
`curl`: `client` с чужим `customerId` — `404`.

Живая проверка Фазы 7.3 (видимость кнопки): при первой загрузке карточки
(`client`, режим приоритизации выключен) — на экране "Режим
приоритизации" и "Скачать Excel", "Сбросить" отсутствует; клик "Режим
приоритизации" — "Сбросить" появляется рядом с "Готово"; клик "Готово" —
"Сбросить" пропадает снова. Тем же URL под `ops` — ни "Режим
приоритизации", ни "Сбросить" не видны вообще ни при каких условиях
(у ops нет переключателя, значит `isPriorityMode` для него никогда не
становится `true`). Временная карточка/пользователи удалены после
проверки.

Живая проверка Фазы 7.2 (целые штуки): первая попытка через
UI-автоматизацию (клик в поле + напечатать "0.02") дала обманчивый
результат — поле уже показывало `10`, клик его не очистил, "0.02" дописалось
к существующему `10`, получив `"100.02"` в самом DOM, что `commit()`
корректно округлил до `100` — не баг компонента, артефакт способа ввода в
автоматизации браузера (`Math.round(100.02) === 100`, проверено отдельно
как явное подтверждение гипотезы). Передиагностировано напрямую через
нативный `input`-event (`HTMLInputElement.prototype.value`-сеттер +
`dispatchEvent(new Event('input'))` — тот же путь, которым React получает
настоящие нажатия клавиш, в обход капризов синтетической клавиатуры в этой
конкретной автоматизации): `"0.02"` на пустом/сброшенном поле → `0`;
`"17.6"` → `18`; "Весь остаток" на остатке `150` → `150`. Debounced
`PATCH` за вводом `"0.02"` вернул `priorityQty: "0"` — дробное значение
не покинуло браузер ни разу. См. корневой README для точных цифр и
`curl`-проверки `400`/`200` на самом бэкенде.

## Готово к отгрузке (Фаза 9)

Пункт меню "Готово к отгрузке": `/client/ready-to-ship` (рабочий инструмент)
и `/ops/ready-to-ship` (тот же вид только для чтения; ops видит клиента —
единственного автоматически, выбор появится, когда клиентов станет больше
одного). Данные — один запрос `GET /ready-to-ship` ("вид раздела"), каждая
мутация возвращает такой же вид и пишется в кэш целиком (`setQueryData`), так
что после действия никаких дополнительных запросов нет. Ошибки — тостом с
настоящим текстом ответа API (`getErrorMessage`).

**Сколько слотов показывается (правка 2026-09-21).** Сервер создаёт слоты только вверх
и не удаляет (Фаза 8), поэтому после недели с меньшей потребностью их остаётся
больше, чем нужно: на проде 47 слотов при `totalPossibleContainers` = 40. Экран
показывает ровно столько свободных слотов, сколько нужно плану:
`totalPossibleContainers` (уже округлён вверх) минус контейнеры, в которых что-то
лежит или которые подтверждены; эти контейнеры не скрываются никогда, даже если их
номер больше потребности (тогда всего их может быть больше `totalPossibleContainers`
только на столько, на сколько клиент заполнил лишних). Тот же список — в выборе
контейнера в окне "Переместить", в плашке "Контейнеров: N" и в карточке "Свободные
слоты". Лишние пустые слоты остаются в БД и просто не видны. Проверено на реальном
файле: 47 слотов в БД → 40 на экране, после `move` 1 в работе + 39 свободных, контейнер
с позицией под номером 45 остаётся виден (2 в работе + 38 свободных = 40).
**Задеплоено на прод 2026-09-21** (только фронтенд, `dist` собран с `VITE_API_URL=/api`,
прежний билд — `/var/www/ceat-frontend.prev`): на реальных данных прода 47 слотов в БД,
`totalPossibleContainers` = 40, экран показывает "Контейнеров: 40", "Свободные
слоты (40)" и 40 вариантов в окне "Переместить".

**Раскладка.** От 1400 px — две колонки (слева список готового, липкий, со
своей прокруткой; справа контейнеры), ниже — друг под другом. Порог 1400, а не
1280, потому что таблица списка (PI/SO, материал, остаток, кнопка) в половине
экрана уже не помещалась и уходила в горизонтальный скролл (проверено на
1024 / 1366 / 1440 / 1600 — горизонтального переполнения нет).

**Блок 1 — список готового.** PI + SO, материал + описание, остаток (и "≈ N
конт."), кнопка "Переместить" (только client). Поиск по материалу, описанию,
PI, SO; сортировка по PI, материалу, остатку. Строка без нагрузки на контейнер
(`loadability` пуст/0) — метка "нельзя разместить" и заблокированная кнопка с
подсказкой (backend вернул бы `400`). "Переместить" — модалка на
react-hook-form + zod: количество (целое, `1…остаток`, кнопка "Всё (N)") и
радио-список контейнеров с текущим заполнением и цветом; у каждого варианта
показано, каким станет заполнение ("→ 97%"), при выходе за 100% — красное
предупреждение (разместить всё равно можно, подтвердить — нет). Последний
выбранный контейнер предзаполняется.

**Блок 2 — контейнеры.** Карточка на каждый заполненный контейнер: метка, крупный
% заполнения и цвет (≤90% обычный, 90–100% жёлтый, >100% красный), строки —
материал, описание, `allocated_qty`, PI. Свободные (пустые) слоты — одной
плашкой внизу. Неподтверждённый контейнер (client): "Убрать" на строке →
`POST /ready-to-ship/remove` (см. корневой README, "Фаза 9: доработки
backend"). Подтверждённый: блок маркировки на каждой строке — статус, загрузка /
замена / скачивание / удаление (client, удаление через confirm), только
скачивание (ops); счётчик "Маркировка: N файл(а/ов) из M". ops у
подтверждённого контейнера видит "Разблокировать" с подтверждением: "после
разблокировки клиент сможет менять состав, файлы маркировки на изменённых
строках будут удалены".

**Панель действий (client, липкая).** Показывается, пока есть что откатывать
(`view.undoableActions > 0` — а не по числу строк: если клиент убрал всё,
"Отменить" должно оставаться): "Отменить одно действие", "Отменить всё" (с
подтверждением), "Подтвердить" (с подтверждением). "Подтвердить" заблокирована,
если есть красный контейнер, с причиной рядом ("Нельзя подтвердить:
перегружены К3 (103%)"); если backend всё-таки вернул `400`, его текст
показывается тостом.

**Проверка на реальных данных.** Прод-данные не трогались (код Фазы 9 там ещё
не выложен) — вместо этого на копии продовой БД (ветка Neon) подняты локальный
backend и Vite: 24 активные карточки, **219 строк** в списке готового. Наполнение
до 50% / 95% / >100% через API, затем в браузере: цвета и порог 90/100, красный
контейнер блокирует "Подтвердить" и снимается перемещением/удалением,
`confirm` → блок маркировки, загрузка/замена/удаление/скачивание файла,
"Разблокировать" под ops, "Убрать" + "Отменить одно действие" (возвращает
удалённое), "Отменить всё". Читаемость: 219 строк — ~2,5 тыс. DOM-узлов, диалог
"Переместить" открывается за ~83 мс, поиск фильтрует без задержки (строки
мемоизированы) — виртуализация не понадобилась. "Нельзя разместить" на копии не
воспроизвести (у всех строк есть нагрузка) — состояние проверено на
синтетических локальных данных.

**Скорость.** Действие с сервером занимает ~2 с (раньше 3+): основное — сетевые
запросы backend → Neon (106 мс на запрос с VPS), см. корневой README, где
описано сокращение числа запросов и `idleTimeoutMillis` пула. Оптимистичного
обновления на фронте нет: состав контейнеров считает сервер (блокировки,
переброс), поэтому ответ показывается только после него; кнопки на время
запроса блокируются.

**Задеплоено на прод 2026-09-19** вместе с backend (`POST /ready-to-ship/remove`
и `undoableActions` без него не работают — выкладывать только парой). Проверено
на реальных 28 карточках, см. корневой README, "Редеплой Фазы 9": в браузере под
временным клиентом страница показала 245 строк, 42 слота, 3 293 шт.; "Переместить"
(диалог → 2,5 с → карточка контейнера 1,6%, панель действий) и "Отменить всё"
(→ 2,5 с, всё вернулось) отработали без ошибок.

(у исторического PI без карточки — просто текст с подсказкой). Файлы: список,
"Скачать" (обе роли; имя файла берётся из ответа и раскодируется), ops — "Удалить"
(с подтверждением) и форма добавления (любой формат, необязательное описание).
ops: поля ETD/ETA с датой из файла под каждым ("В файле: …" / "В файле даты нет"),
"Сохранить даты" шлёт только изменившиеся поля; пустое поле у ручной даты снимает
именно её; "Сбросить до данных файла" (с подтверждением) виден только пока есть
хотя бы одна ручная дата.

**Отправлено на карточке PI.** Строка "Всего / Ожидает / Отправлено" над блоком
файлов детальной страницы PI (shippedQty из ответа); 0 показывается как 0 — "пока
ничего не отправлено" тоже информация.

**Мелочи, найденные при живом тесте.** Даты (date-колонки, YYYY-MM-DD) форматируются
без `new Date(...)` (`formatDay`), иначе к западу от Гринвича показывались бы на день
раньше. Запросы контейнеров не повторяются при 4xx (`retryUnlessClientError`) — иначе
сообщение "не найден" появлялось бы через ~7 с стандартных повторов.

**Проверено вживую** (реальный MTK_ROSBERG_INR.xlsx, загруженный в локальную БД —
ветка Neon к этому моменту была удалена; на проде на момент Фазы 11 контейнеров ещё
нет): 77 контейнеров, сортировка по ETA, 6 контейнеров с бейджами ETA-15; деталь с 10
строками и итогом; правка дат ops (в списке — янтарный цвет, карандаш и подсказка;
client видит те же пометки без редактора), снятие одной даты, сброс с
подтверждением; загрузка файла ops, скачивание обеими ролями (те же байты, имя
packing list.txt), удаление с подтверждением; ошибка 404 показывается текстом
API; чужой клиент видит пустой список с пояснением и "не найден" на чужой контейнер;
Отправлено на карточке PI совпало с ответом API (998 = 998.00). Раскладка при
1024 px: страница не выходит за ширину, таблица списка прокручивается внутри
карточки. **Задеплоено на прод 2026-09-21 вместе с backend; финальная проверка
на реальных данных прода (68 контейнеров) пройдена** — см. корневой README, "Редеплой
Фазы 11".

**Известное по данным.** У 6 контейнеров из ETA-15 в листе ETD-ETA ETA пуст, а в
ETA-15 стоит 2026-09-20 — бэкенд теперь подставляет её (и ETD) как запасной источник,
см. корневой README, "Фаза 10"; у контейнеров, где даты нет нигде, остаётся прочерк.
Documents release показывается как есть (0).

## Название карточки PI (label; после Фазы 11, задеплоено на прод 2026-09-21)

Выложено вместе с backend (коммит `444fbc9`, прежний билд — `/var/www/ceat-frontend.prev`);
подробности — корневой README.

Везде, где показан номер PI, — `«100039270: Орел»`, а без названия просто номер (без
двоеточия). Один хелпер, `formatPiTitle(piNumber, label)` в `lib/format.ts`; он же в
плитке списка (`PiCard`), шапке карточки (`PiDetailPage`), "Готово к отгрузке"
(`ReadyLinesTable` — заодно поиск теперь ищет и по названию, `ContainerCard`,
`MoveDialog`, `RemoveDialog`), колонке PI фактического контейнера
(`ActualContainerDetailPage` берёт название из кэша списка PI) и в тосте загрузки
проформы. Типы: `label` в `ProformaInvoice`, `piLabel` в `UnallocatedLine` и
`ContainerAllocation`.

**Редактор** (`PiLabelEditor`, мутация `useUpdateLabelMutation` — `PATCH /proforma-invoices/:id/label`).
Рядом с номером в шапке карточки, только для client и только пока нет
`signedFileUrl`: поле (`maxLength` 30) и "Сохранить" (активна, пока текст отличается от
сохранённого; пустое поле сохраняется как "без названия"). Ответ пишется в кэш карточки
(`setQueryData`), список обновляется; на ошибку — тост с текстом API, и список
перезапрашивается (если проформу успели подписать, поле пропадёт). После подписания
редактор не рендерится вовсе: заголовок — обычный текст, никаких подсказок про
разблокировку. У ops редактора нет ни при каких условиях.

**Проверено вживую** (локальная БД, миграция накатана): плитки `100037314: Орел` /
`100038680: Сокол-2`, у остальных — только номер; у client на неподписанной карточке поле
и "Сохранить" (кнопка неактивна, пока текст не изменён; сохранение → `PATCH …/label` 200
и тост "Название сохранено", в списке название появилось), на подписанной поля нет; у ops
поля нет, заголовок с названием; в "Готово к отгрузке" — строки, карточка контейнера,
диалоги "Переместить" и "Убрать" с `PI 100037314: Орел · …`, поиск "орел" оставляет только
эти строки; в детали фактического контейнера — ссылка `100038680: Сокол-2`. Нажатие Enter
в поле через автоматизированный браузер форму не отправило (синтетический Return), кнопка
"Сохранить" работает.

## Двуязычный интерфейс EN / RU (react-i18next; не задеплоено)

Все статичные тексты интерфейса вынесены в `src/i18n/locales/en.json` и `ru.json`
(вложенные ключи по разделам: `common`, `nav`, `login`, `piList`, `piCard`, `piDetail`,
`readyToShip`, `shipped`, `backorder`, …); инициализация — `src/i18n/index.ts`
(`i18next` + `react-i18next`, ресурсы встроены, `initAsync: false`).

- **Язык по умолчанию — всегда английский.** Определения по браузеру/системе нет.
  Выбор хранится в `localStorage` под ключом `ui-lang` (`en` | `ru`); любое другое или
  отсутствующее значение → `en`. `<html lang>` переключается вместе с языком.
- **Переключатель** `EN | RU` (`components/LanguageSwitcher.tsx`) — в боковом меню обеих
  ролей, после пунктов навигации и перед «Выйти» / «Log out», отделён линиями. Боковое меню
  теперь `sticky` на высоту окна, чтобы переключатель и «Выйти» были видны и на длинных
  страницах (раньше они оказывались в самом низу прокручиваемой страницы). На странице входа
  переключателя нет (язык запоминается после первого выбора).
- **Переименования** (вместе с переносом): раздел «Готовые контейнеры» → RU «Отгружено» /
  EN «Shipped» (пункт меню и заголовок списка; описание — «Отгружено по данным
  еженедельного файла.» / «Shipped, based on the weekly file.», без пояснений про карандаш и
  зелёный цвет); «Мои PI» / «PI» и заголовки «Проформы» / «Мои проформы» → одно название для
  обеих ролей, RU «Проформа-инвойс» / EN «Proforma Invoices»; переключатель приоритета
  (выключен) → RU «Приоритет» / EN «Priority» (включён: «Готово» / «Done»).
- Заодно: «Close» в диалогах переведён («Закрыть»); название клиента в меню client берётся
  из данных (`GET /customers` скоуплен на своего клиента), а не захардкожено «MTK Rosberg»
  (пока не загрузилось — «Клиент» / «Client»); числа форматируются по языку (`1,234.5` /
  `1 234,5`), даты остались в формате `дд.мм.гггг` в обоих языках.
- Множественное число («Маркировка: N файла из M») — через плюрализацию i18next
  (`markingCounter_one/_few/_many/_other`); прежняя `pluralFiles` удалена.
- Форма в диалогах «Переместить» / «Убрать» перепроверяется при смене языка, поэтому уже
  показанное сообщение об ошибке пересобирается на новом языке.
- **Метки слотов «Контейнер N»** в разделе «Готово к отгрузке» — в БД остаются как есть, а на
  экране имя строится по номеру: `useContainerName()` (`lib/readyToShip.ts`) вытаскивает N из
  метки (`Контейнер N` / `Container N`, как `containerCell()` в Excel-выгрузке на backend) и
  показывает `t("readyToShip.containerLabel", { n })` — «Контейнер 3» / «Container 3». Метка
  другого вида (свой текст) показывается как есть. Применено везде, где выводилась
  `container.label`: заголовок карточки контейнера, свободные слоты, диалоги «Переместить» /
  «Убрать» / «Разблокировать», тосты, причина «Нельзя подтвердить: перегружены …», удаление
  файла маркировки. Атрибут `data-container-label` остаётся с сырой меткой.
- **Не переводилось (намеренно):** содержимое Excel-выгрузок и любые тексты от backend
  (сообщения об ошибках API, названия PI, названия клиентов).
- **Проверено вживую:** на чистом `localStorage` — английский (и при некорректном значении
  `ui-lang`); переключение в обе стороны без перезагрузки на входе, списке PI, детали PI
  (режим приоритета, поле названия), «Готово к отгрузке» (панель действий, диалоги
  «Переместить» / «Убрать» / «Подтвердить» / «Отменить всё»), «Отгружено» (список и деталь),
  «Загрузка бэкордера», у обеих ролей; выбор сохраняется после перезагрузки. Скрипт сверки
  ключей: во всех вызовах `t(...)` ключи существуют, наборы ключей en/ru совпадают.

## Известные ограничения этой фазы

- Автотестов на фронтенде по-прежнему нет (нет vitest/RTL) — Фаза 9
  проверялась `tsc -b`, `oxlint`, `vite build` и ручным прогоном в браузере
  на реальных данных (см. выше); логика заполнения/состава живёт на backend
  (190 юнит-тестов).
- Dev-сервер Vite после добавления новых зависимостей (в Фазе 9 — `zod`,
  `@hookform/resolvers`) нужно перезапустить: иначе белая страница и "Invalid
  hook call … useAuth must be used within an AuthProvider" (два экземпляра
  React из-за устаревшего pre-bundle).

- Нет real-time обновлений — инвалидация react-query после мутаций,
  никакого веб-сокета/поллинга (осознанно не просили).
- Нет пагинации на списке карточек (23 штуки — пилотный масштаб).
- Нет drag-drop загрузки — обычный `<input type="file">`.
- `PiAdditionalFile` по-прежнему не имеет отдельного экрана
  списка/удаления — только добавление через детальную страницу PI (совпадает
  с тем, что на бэкенде у него нет отдельного контроллера, см. корневой
  README).
- Прод (`<server-ip>`) всё ещё раздаёт v1-фронтенд — не тронут этой
  фазой.
